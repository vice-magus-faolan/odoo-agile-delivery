Agile Git Facts

View repository, branch, commit, pull-request and check observations alongside Odoo 19 Community Projects and tasks. This addon depends on project_agile; install project_agile_git_github to receive signed GitHub deliveries.

Repositories belong to one Agile-enabled Project and inherit its company. Project users read facts within their Project visibility and allowed companies; Project administrators configure repositories and inspect deliveries. Task buttons show facts associated with explicit Agile keys, such as ENG-142.

Git facts report provider observations. Continue to review and complete tasks through your Project workflow; stage application belongs to the separately configured project_agile_git_automation addon.

Installation

Follow the repository installation guide.

Configuration

Repository configuration requires Administrator under Project in the user access rights. The instructions below call this role Project administrator. Setting Webhook Secret also requires System Administrator access.

  1. Enable Agile on the Project and configure its stable task-key prefix.
  2. Open Project > Tasks > Git Repositories and create a repository. Enter Name, Provider, Provider Repository Id, Project and Canonical Url. Company follows the selected Project.
  3. For GitHub, run gh api repos/OWNER/REPO --jq .id and enter the returned number in Provider Repository Id. Each provider repository can be mapped only once.
  4. Set Canonical Url to the HTTPS repository URL on github.com, gitlab.com or bitbucket.org, matching Provider, for example https://github.com/example/delivery. Fact links are derived from this URL. Keep it aligned with the provider repository identity.
  5. Choose Retention Policy before receiving deliveries. Digest Only is the default. GitHub asynchronous processing needs Redacted Excerpt; changing the setting later cannot restore payloads for earlier deliveries.
  6. For GitHub deliveries, follow the GitHub connector configuration.

Redacted excerpts can still contain sensitive business text and unrecognized credentials. Keep secrets out of commit messages and other webhook text.

Environment branch mappings

As a Project administrator with write access to the Project, first configure its environments in the Project settings. Flag each production environment with Production; the name does not determine its role.

Open Project > Configuration > Environment Git Branches. Select an Environment and a Repository from the same Agile Project and enter Target branch as the exact, case-sensitive short branch name, for example release/uat, not refs/heads/release/uat. Each environment maps a repository once. Edit or reactivate that mapping instead of adding a duplicate.

Configure every repository needed for that environment and at least one production mapping before using the UAT/no-production filter. Archived mappings, repositories and environments are excluded. Mapping edits immediately reinterpret retained PR observations. Project copies start without mappings.

Usage

  1. Open an Agile-enabled Project and choose Repositories to see its repositories. Open one and use Branches, Commits, Pull Requests or Checks to inspect the observations and follow their provider links.
  2. Open an Agile task and use the same fact buttons to see observations linked to its stable Agile key. Visibility and counters follow your access rights. The GitHub connector guide explains which source fields can establish links.
  3. As a Project administrator, open the repository and choose Deliveries. Inspect Provider Delivery Id, Event Type, State, Attempt Count, Next Retry At and Error Summary when facts have not appeared.

Facts are read-only observations. Ordering State identifies Stale or Ambiguous source ordering when an incoming observation cannot safely replace current values. Review the provider record and delivery details before acting on those observations.

To stop future GitHub deliveries, archive the repository. Existing deliveries and facts remain, and already queued work can still be processed.

Historical environment merges

The task Git Merge Evidence tab shows one line per configured environment: linked PRs with Known ordering merged into its exact mapped branch, or no merge seen. It is hidden without visible active mappings. Observed merged PRs opens source details. In Tasks search, Merged into, not Production finds tasks with a merge into the selected environment but none into any visible production mapping in that Project; a production mapping is required. Typed names match the whole name, ignoring case, so UAT does not match Pre-UAT. The tab and filter follow your access rights; the BA’s manual Environments panel stays separate.

A merge is not a deployment or proof that all task code is present. Only PRs linked by task keys in their title, body or head branch count: put promoted task keys in the release PR body when merging UAT into Production. The GitHub connector considers the first 100 distinct body keys and records an overflow audit beyond that limit. Split larger releases across PRs to retain all links; see the GitHub connector guide for key eligibility and other source limits. A late source event can hide a merge until a strictly newer, unambiguous event arrives; no merge seen does not prove absence.

Bug Tracker

Bugs are tracked on GitHub Issues. In case of trouble, please check there if your issue has already been reported. If you spotted it first, help us to smash it by providing a detailed and welcomed feedback.
