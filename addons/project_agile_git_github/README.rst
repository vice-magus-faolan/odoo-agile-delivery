Receive authenticated GitHub webhooks into the Git delivery ledger, then
normalize supported events through native Odoo scheduled actions. This
optional Odoo 19 Community addon depends on ``project_agile_git``.

Supported events are ``push``, ``pull_request`` and ``check_run``.
Processing records branches, commits, pull requests, checks and explicit
task-key associations. GitHub receipt and processing leave task
completion and stage decisions to your Project workflow and the
separately configured policy addon.

Installation
============

Follow the `repository installation
guide <https://github.com/vice-magus-faolan/odoo-agile-delivery/blob/main/README.md#installation>`__.

Configuration
=============

First configure the repository using the `Git Facts
guide <https://github.com/vice-magus-faolan/odoo-agile-delivery/tree/main/addons/project_agile_git#configuration>`__.
Repository configuration and delivery recovery require **Administrator**
under **Project** in the user access rights, called Project
administrator below. The person setting **Webhook Secret** must also
have System Administrator access. GitHub webhook setup requires
permission to administer that repository webhook.

1. In **Project > Tasks > Git Repositories**, select the intended
   repository. Set **Provider** to **GitHub**, check **Project** and
   **Company**, and verify **Provider Repository Id** matches GitHub
   ``repository.id``. Keep the repository active and set **Canonical
   Url** to its ``https://github.com/`` repository URL.
2. Select **Redacted Excerpt** in **Retention Policy** before sending
   events. **Digest Only** records receipt metadata but leaves no
   payload for scheduled normalization or later reprocessing. Changing
   the setting does not repair earlier receipts or an exact redelivery
   of the same delivery ID.
3. As a System Administrator with the Project access above, set
   **Webhook Secret** and save. In GitHub, configure the same secret,
   select ``application/json``, and use your externally reachable HTTPS
   Odoo URL followed by ``/project_agile_git_github/webhook``. Select
   ``push``, ``pull_request`` and ``check_run`` events as required, with
   the necessary GitHub permissions.
4. Ensure native Odoo scheduled actions are running. **Normalize Agile
   GitHub Deliveries** is configured every minute, processing at most 20
   deliveries per invocation. Actual latency depends on scheduler
   availability and backlog. **Purge Expired Agile GitHub Payload
   Excerpts** is configured daily.

Ingress requires ``X-GitHub-Event``, ``X-GitHub-Delivery`` and an
exact-body ``X-Hub-Signature-256`` HMAC SHA-256 signature. Requests are
limited to 256 KiB. An accepted receipt returns HTTP 202; this confirms
ledger receipt, not successful normalization. An exact duplicate uses
the same ledger row. A reused delivery ID with different event type,
body digest or size returns HTTP 409.

A retained redacted JSON excerpt must fit within 4,096 characters; an
oversized excerpt produces a **Failed** delivery with a diagnostic and
no retained payload. Redaction removes recognized credentials but may
leave sensitive text or unknown credential formats. Keep such content
out of webhook fields and do not copy payloads or secrets into chatter,
tickets or routine exports. Secret and retained payload access is
restricted to System Administrators.

Usage
=====

Link facts to tasks
-------------------

Use an existing task key such as ``ENG-142`` in one of these supported
source fields:

- ``push``: branch ref and each commit message;
- ``pull_request``: title, body and head branch;
- ``check_run``: name and output title.

For example, use branch ``feature/ENG-142-oauth`` or commit message
``ENG-142: Add OAuth callback``. Keys use an uppercase prefix of 2 to 10
letters or digits starting with a letter, a hyphen, and a positive
decimal suffix. Separate the key from surrounding word characters.
Matching is limited to active tasks in the configured repository Project
and company. Task names and Odoo database IDs do not establish links.
Source text is bounded to 4,096 characters with at most 20 distinct keys
per source field.

After scheduled processing, open the task and choose **Branches**,
**Commits**, **Pull Requests** or **Checks** to inspect its linked
facts. A missing link can mean the key was unknown, invalid, excessive
or referred to archived work.

Inspect and recover deliveries
------------------------------

As a Project administrator, open **Project > Tasks > Git Repositories**,
select the repository and choose **Deliveries**. Inspect **Provider
Delivery Id**, **Event Type**, **State**, **Attempt Count**, **Next
Retry At**, **Payload Sha256** and **Error Summary**. **Replay Mismatch
Count** and **Last Replay Mismatch At** identify conflicting reuse of a
delivery ID.

- **Queued** awaits scheduled processing. **Processing** has a
  five-minute lease; an expired lease becomes eligible for another
  claim.
- **Retryable** awaits **Next Retry At**. Transient failures use
  exponential backoff starting at one minute and capped at one hour,
  becoming **Failed** when the attempt count reaches five. Malformed
  payloads fail without automatic retries; unsupported events with
  retained payloads become **Discarded**.
- **Processed** records completed normalization. Inspect task-linked
  facts to see the observations and their source ordering.
- After correcting the cause of a **Failed** or **Discarded** delivery,
  choose **Reprocess** only if a retained payload is still available. It
  requeues the same ledger row and preserves the attempt count; it does
  not provide a fresh five-attempt budget. A new transient failure at or
  above five attempts is terminal. Repeating an unsupported event will
  not add support for it.

Digest-only, oversized-excerpt and purged deliveries have no payload to
reprocess. Arrange a new provider delivery after correcting
configuration; exact redelivery of an old receipt does not fill its
missing payload.

Retained excerpts receive a 30-day expiry. Daily cleanup removes expired
excerpts only from **Processed** or **Discarded** deliveries, in batches
of at most 100. **Retained Payload Purged At** records cleanup; the
ledger, digest, facts and association audit remain. **Queued**,
**Processing**, **Retryable** and **Failed** payloads are retained for
recovery even after expiry. Have a System Administrator investigate
scheduler or retention problems through normal Odoo administration.
