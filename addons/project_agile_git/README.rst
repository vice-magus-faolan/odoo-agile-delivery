View repository, branch, commit, pull-request and check observations
alongside Odoo 19 Community Projects and tasks. This addon depends on
``project_agile``; install ``project_agile_git_github`` to receive
signed GitHub deliveries.

Repositories belong to one Agile-enabled Project and inherit its
company. Project users read facts within their Project visibility and
allowed companies; Project administrators configure repositories and
inspect deliveries. Task buttons show facts associated with explicit
Agile keys, such as ``ENG-142``.

Git facts report provider observations. Continue to review and complete
tasks through your Project workflow; stage application belongs to the
separately configured ``project_agile_git_automation`` addon.

Installation
============

Follow the `repository installation
guide <https://github.com/vice-magus-faolan/odoo-agile-delivery/blob/main/README.md#installation>`__.

Configuration
=============

Repository configuration requires **Administrator** under **Project** in
the user access rights. The instructions below call this role Project
administrator. Setting **Webhook Secret** also requires System
Administrator access.

1. Enable Agile on the Project and configure its stable task-key prefix.
2. Open **Project > Tasks > Git Repositories** and create a repository.
   Enter **Name**, **Provider**, **Provider Repository Id**, **Project**
   and **Canonical Url**. **Company** follows the selected Project.
3. For GitHub, run ``gh api repos/OWNER/REPO --jq .id`` and enter the
   returned number in **Provider Repository Id**. Each provider
   repository can be mapped only once.
4. Set **Canonical Url** to the HTTPS repository URL on ``github.com``,
   ``gitlab.com`` or ``bitbucket.org``, matching **Provider**, for
   example ``https://github.com/example/delivery``. Fact links are
   derived from this URL. Keep it aligned with the provider repository
   identity.
5. Choose **Retention Policy** before receiving deliveries. **Digest
   Only** is the default. GitHub asynchronous processing needs
   **Redacted Excerpt**; changing the setting later cannot restore
   payloads for earlier deliveries.
6. For GitHub deliveries, follow the `GitHub connector
   configuration <https://github.com/vice-magus-faolan/odoo-agile-delivery/tree/main/addons/project_agile_git_github#configuration>`__.

Redacted excerpts can still contain sensitive business text and
unrecognized credentials. Keep secrets out of commit messages and other
webhook text.

Environment branch mappings
---------------------------

As a Project administrator with write access to the Project, first
configure its environments in the Project settings. Flag each production
environment with **Production**; the name does not determine its role.

Open **Project > Tasks > Environment Git Branches**. Select an
**Environment** and a **Repository** from the same Agile Project and
enter **Target branch** as the exact, case-sensitive short branch name,
for example ``release/uat``, not ``refs/heads/release/uat``. Each
environment maps a repository once. Edit or reactivate that mapping
instead of adding a duplicate.

Configure every repository needed for that environment and at least one
production mapping before using the UAT/no-production filter. Archived
mappings, repositories and environments are excluded. Mapping edits
immediately reinterpret retained PR observations. Project copies start
without mappings.

Usage
=====

1. Open an Agile-enabled Project and choose **Repositories** to see its
   repositories. Open one and use **Branches**, **Commits**, **Pull
   Requests** or **Checks** to inspect the observations and follow their
   provider links.
2. Open an Agile task and use the same fact buttons to see observations
   linked to its stable Agile key. Visibility and counters follow your
   access rights. The GitHub connector guide explains which source
   fields can establish links.
3. As a Project administrator, open the repository and choose
   **Deliveries**. Inspect **Provider Delivery Id**, **Event Type**,
   **State**, **Attempt Count**, **Next Retry At** and **Error Summary**
   when facts have not appeared.

Facts are read-only observations. **Ordering State** identifies
**Stale** or **Ambiguous** source ordering when an incoming observation
cannot safely replace current values. Review the provider record and
delivery details before acting on those observations.

To stop future GitHub deliveries, archive the repository. Existing
deliveries and facts remain, and already queued work can still be
processed.

Historical environment merges
-----------------------------

Open the task **Git Merge Evidence** tab. **Merge observed in** shows
the configured environments with at least one linked, known merged PR
targeting their exact branch. **Observed merged PRs** opens those PR
records, including provider links and retained provenance. The details
identify the repository, branch, PR, merge time, source time, last-seen
time and confidence.

One merged PR is partial task progress even if another is open,
uncertain or in another repository. No links are unknown; no visible
active mapping is unconfigured. A merge is historical evidence, not a
deployment, current code presence or proof that all work for the task
has arrived. Reverts, reapplications, cherry-picks, promotions, branch
deletion, force-push and renames do not infer current presence or
absence. A head SHA is not a merge SHA.

In Tasks search, select **UAT merge observed; no production merge
observed (visible evidence)** and choose the exact UAT environment.
Typing a name matches the whole name, ignoring case, not a substring
such as Pre-UAT. The filter requires a visible active production mapping
in the same Project and excludes a task with any qualifying visible
production merge, even from a different PR. A missing or uncertain
production observation can leave a task included as unknown, never as
proof that its code is absent. Results follow your current Task,
Project, environment, repository, mapping, association and PR access.

Only **Known** ordering can establish a positive. **Stale** and
**Ambiguous** remain uncertain until a strictly newer unambiguous
observation arrives. This conservative rule can hide a genuine merge
after an otherwise harmless late event. Delayed, failed, digest-only or
prematurely purged deliveries are not backfilled by inference. Purging
an already processed payload leaves normalized merge facts readable.

The separate manual **Environments** panel remains authoritative for BA
Configuration and Data import status. Git evidence never updates those
lines, their actor/time/history, stages or task completion.
