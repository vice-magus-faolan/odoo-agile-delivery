Optional Odoo 19 Community-compatible Git workflow policies, depending
only on ``project_agile_git``. The addon is LGPL-3 and uses native Odoo
scheduled actions; GitHub, Scrum, an external queue runner and outbound
provider calls are not required. A separately configured ingress adapter
supplies authenticated facts.

Projects start disabled and in dry-run mode. Rules describe a merged
pull request on an exact branch, allowed source stages, one target stage
and optional named checks. Two different authorized people must author
and approve a revision. Dry runs record informational decisions and
never move tasks. Separately enabled Apply mode can move only the
approved task stage under the approved execution user; it cannot mark
native completion, change Sprint scope or edit estimates.

Installation
============

Follow the `repository installation
guide <https://github.com/vice-magus-faolan/odoo-agile-delivery/blob/19.0/README.md#installation>`__.

Configuration
=============

Installation assigns no **Git Policy Manager** members and creates no
rules. An authorized administrator must explicitly grant that capability
to the rule owner and a different approver. It includes Project
administrator permissions; Project administrator access alone is not
sufficient. Use an active internal, non-superuser execution account with
current company membership and actual write access to all affected
Project tasks.

1. Configure an active company-scoped Agile Project and a repository
   using the `Git Facts
   guide <https://github.com/vice-magus-faolan/odoo-agile-delivery/tree/19.0/addons/project_agile_git#configuration>`__.

2. As a Git Policy Manager, open the Project form, **Git Policy**, and
   choose **Enable Dry Run**. Do not select Apply mode for a preview.

3. As the intended rule owner, open **Project > Configuration > Git
   Policy Rules**. Create a named rule and select its repository; Odoo
   records you as its owner. Then create its draft revision under **Git
   Policy Revisions**. Select:

   - the rule and exact target branch;
   - 1 to 20 active source stages shared with that Project, not a user's
     personal stages;
   - one active shared target stage outside the source selection,
     without rating, email or SMS templates;
   - up to 20 distinct exact check names, each 1 to 255 characters;
   - an active internal execution user, not a superuser or portal
     account, with company membership and actual access to every
     affected Task.

   No check names means CI is not a condition, not that CI passed.

4. A different Git Policy Manager opens the revision and chooses
   **Approve and Activate**, acknowledges the native side effects, then
   confirms. Review the saved mode and cutoff: approval in Dry Run does
   not enable task writes.

If activation refuses the installed access rules or Task configuration,
compare them with `supported permissions and
extensions <https://github.com/vice-magus-faolan/odoo-agile-delivery/blob/19.0/docs/git-policy-authority-profiles.md>`__
before approval; additional extensions can have external effects a stage
write cannot undo. See the `configuration
guide <https://github.com/vice-magus-faolan/odoo-agile-delivery/blob/19.0/docs/git-policy-configuration.md>`__
for supported selectors and revocation conditions.

Usage
=====

As a Git Policy Manager, open **Project > Tasks > Git Repositories**,
select the repository and choose **Evaluate Dry Run (20 PRs)**, or
choose **Preview Repository (20 PRs)** on a rule. Inspect the resulting
decisions, their outcomes and reasons. **Project > Configuration > Git
Policy Dry Runs** lists history. The button examines only the first
page, not every PR; the `dry-run
guide <https://github.com/vice-magus-faolan/odoo-agile-delivery/blob/19.0/docs/git-policy-dry-run.md>`__
describes pagination and exact evidence requirements.

For a meaningful preview, use an eligible merged PR on the configured
branch with task keys linked by the ingress adapter. Both merge and
original receipt must be later than the approval cutoff, with fresh
source timestamps and any required successful checks on the exact PR
head. If several provider checks have the same required name, that named
check is not treated as passed, even if one run succeeded. After a
matching check arrives, explicitly evaluate again to obtain a new
decision; a preview does not move tasks or approve later task changes.

Check the dry-run decisions before enabling task changes, and obtain the
required operator approval. Choosing **Select Apply Mode** revokes
existing approval: create a **New Revision** and obtain distinct-person
approval with a fresh cutoff. Earlier merges cannot be backfilled.
Native stage writes can generate tracking messages and notifications,
change timestamps and durations, and recompute nonterminal state. They
do not set native Done state. Odoo.sh scheduling is best effort, not a
one-minute SLA; backlog and retry limits can prevent otherwise eligible
work from executing.

Use **View Attempts** on the Project for state, reason and retry
diagnostics. **Retry Transient Failure** only requeues an eligible
unchanged transient attempt, without resetting the limit of five
processing tries. Waiting for checks uses those same tries. Terminal
attempts cannot be revived. If authority or configuration is wrong,
choose **Emergency Disable** on the Project or **Disable Rule**, correct
the cause and create and approve a new revision. Restoring old access
does not restore revoked approval. Disable stops future work; it does
not undo committed task changes or queued notifications.

Before update, rollback or uninstall, disable policies and preserve
database and filestore backups plus approval, attempt and
consumed-effect history. Uninstall deletes policy history; reinstall
does not restore approvals. Restoring a backup without **Consumed
Effects** can move the same tasks twice. Keep policies disabled while
reconciling that history, then approve a new revision with a new cutoff
instead of re-enabling an old approval. Follow the `operations
runbook <https://github.com/vice-magus-faolan/odoo-agile-delivery/blob/19.0/docs/runbooks/git-policy-operations.md>`__
for recovery, history retention and Odoo.sh staging precautions, and the
`apply
boundary <https://github.com/vice-magus-faolan/odoo-agile-delivery/blob/19.0/docs/git-policy-apply-boundary.md>`__
for compatibility and native side effects.
