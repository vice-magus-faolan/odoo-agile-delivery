Scrum Project Foundation

Scrum Project Foundation (project_scrum) adds Agile teams, Sprints and historical scope evidence to Odoo 19 Community Project. It extends native Project tasks through Agile Project Core, its sole direct dependency. Both addons are LGPL-3; native project is a transitive dependency.

Use ordinary Odoo lists, forms and actions to plan work, start a Sprint, record scope changes and close unfinished work explicitly. One Sprint may be active per Project and Agile team; different teams can have active Sprints in the same Project. Analytics, the interactive planning board and document integrations are optional separate addons.

Installation

Follow the repository installation guide for Odoo 19 and this repository’s addons/ source. As an authorized administrator, update the Apps list, remove the default Apps filter and search for project_scrum (Scrum Project Foundation). It has application=False; installing it also installs project_agile and native Project dependencies.

No Enterprise, OCA Document Page or external queue service is required for Scrum. Back up an existing database and filestore before updates or removal; uninstalling destroys addon-owned Sprint/history data. Use the existing contributor checks for disposable development verification, not a shared operational database.

Configuration

  1. Configure an Agile-enabled Project, key, default item type and estimation method using the Agile core configuration.
  2. As a Project administrator (project.group_project_manager), open Project Configuration > Agile Teams. Create a named team and select that Project. The team belongs to one Project and inherits its company; it is not a separate user-membership or permission configuration.
  3. In Configuration > Agile Item Types, open each type you plan to schedule and review Can Schedule In Sprint. The field defaults to enabled. Disable it for types you want to keep outside Sprints, before assigning tasks of those types. A type already used by a scheduled task cannot be made ineligible.
  4. Open Sprints in Project and create a Sprint with a name, the same Project and its Team. Set Date Start, Date End and a Goal. The end date cannot precede the start date. Save it in Draft before assigning work.

Project users can read teams, Sprints and scope history within their permitted company/Project visibility. Project administrators manage teams/Sprints and use the assignment/close wizards; they also need access to all affected tasks. Task edits retain native Project access checks. A team does not itself grant Project access.

Usage

Plan a draft Sprint

Open the Sprint and choose Product Backlog. This action is scoped to its Project and shows only unscheduled tasks whose Agile Item Type permits Sprint scheduling. Typeless tasks are not eligible. Create work in the Agile Project, set its item type, acceptance criteria and estimate, then prioritize with the backlog list handle.

As a Project administrator, select unscheduled tasks from one Project and use Actions > Assign to Sprint. Select the Draft Sprint and choose Apply. The ordinary assignment wizard also accepts Active Sprints, recording added scope. Alternatively, edit a task’s Sprint field subject to normal task write access. Tasks can join only a Draft or Active Sprint in their own Project and company.

Choose Sprint Backlog on the Sprint to review assigned work. To return selected assigned tasks, use Actions > Remove from Sprint and Apply. The general Project Product Backlog menu is the Agile core backlog, not this Sprint-scoped unscheduled queue.

Start and work

Choose Start Sprint on the Draft Sprint as a Project administrator. Another Active Sprint for the same Project/team must be closed first. Starting freezes the original committed task set and records Committed scope events. Tasks already in native Done state also receive completion evidence.

During the Active Sprint, assignment changes record Added or Removed events; changed estimates record Reestimated with the previous and new story points. Moving a task into native Done (1_done) records Completed; moving out records Reopened. A stage name alone is not the native Done state. Repeated unchanged writes do not add completion events.

Close and read history

Choose Close Sprint as a Project administrator. If unfinished tasks remain, choose Move to Product Backlog or Move to Draft Sprint in the wizard, then confirm Close Sprint. A carry-over target must be a different Draft Sprint for the same Project, company and team. Every task not in native Done state counts as unfinished, including canceled tasks. Closing checks the whole unfinished selection, including archived tasks; hidden or unwritable work must not be silently omitted.

The close records Carried to Product Backlog or Carried to Draft Sprint evidence and moves unfinished work atomically. Completed work stays assigned to the closed Sprint. With no unfinished work, the action closes directly.

Read Scope History on the Sprint for task-level events, observed points, actor, time and carry-over target (an optional list column). This ledger preserves original commitment and subsequent changes rather than reconstructing the past from current task membership. It is read-only in ordinary workflow. Closed Sprint records and assignments are frozen for ordinary users; later native task state/estimate changes do not rewrite the closed scope ledger. There is no ordinary reopen action.

Bug Tracker
